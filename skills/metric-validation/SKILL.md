# 指標は「測っているつもりのもの」を測っているか

## なぜこれが要るのか

指標が間違っている典型は、計算ミスではなく **定義のすり替え**である。
式は正しく動き、テストは通り、出てくる数値ももっともらしい。ただ、
その数値が上下する理由が、意図した性質とは別のところにある。

これが厄介なのは、**自分で書いたテストでは捕まらない**ため。
テストケースは指標を作ったのと同じ直感が選ぶので、
「意図した性質」と「実際に測っている量」がたまたま一致する例ばかりになる。
両者がずれる例は、ずれることに気づいていないから思いつかない。

だから必要なのは、テストを増やすことではなく、**ずれを狙って作りにいくこと**。

## 原則1: 指標を「問い」に言い換える

式ではなく、答えたい問いを一文で書く。名前ではなく問いにするのが要点で、
名前は願望を書けるが、問いは検証できる。

- ✗「`bulge_ratio` は中膨れの度合い」（名前の言い換えでしかない）
- ○「この板は**中央が両端より太いか**を答えたい」

問いにすると、式がその問いに答えているかを直接照合できるようになる。
上の例では式が `中央 / 両端の平均` だったが、問いは「両端**より**」なので、
比べる相手が違う。ここで既にずれが見える。

## 原則2: その数値が上がる「別の理由」を数える

指標 M で性質 P を見たいとき、**M を大きくする経路を P 以外に列挙する**。
1 つでも挙がれば、それが交絡因子であり、弁別ケースの材料になる。

| 指標 | 意図した理由 | 別の理由（交絡） |
|---|---|---|
| 中央幅 ÷ 両端平均 | 中央が太い | 細り方が非線形（終盤で急に細る） |
| 頭部中心からの 3D 距離 | 外側の層にある | 下に長く垂れている |
| 「幾何法線」と放射方向の角度 | 形状が変わった | API が実はカスタム法線を返している |
| チェーン根の親ボーン | 髪が何にぶら下がるか | 「チェーン」に何を含めたかで変わる |

**API・ライブラリが返す値も交絡因子になる。** 名前が `geometric_normal` でも、
その処理系のその条件下で本当に幾何量を返すとは限らない。
名前を信用せず、**入力の片方だけを動かして出力が動くか**を見る。

## 原則3: 閾値の問題か、判別式の問題かを切り分ける

これが一番効く。手順は単純:

1. **本物の陽性**（性質 P がある入力）と **偽陽性**（P は無いが交絡だけある入力）を作る
2. 両方でスコアを出す
3. **偽陽性のスコアが本物以上なら、どんな閾値を選んでも分離できない**

分離できないなら、直すべきは閾値ではなく式そのもの。
逆に順序が保たれていれば、閾値の校正で足りる。

実例: 本物の中膨れが **1.193**、単調に細るだけの偽陽性が **1.453**。
偽陽性の方が高い。この時点で閾値の調整は無意味だと確定する。

**「閾値を上げれば直る」と思ったら、必ずこのテストを先に通す。**
閾値いじりは、判別式の誤りを隠したまま数字だけ合わせてしまう。

## 原則4: 構造上の定数と、恒等崩壊を疑う

指標が **入力によらず必ず同じ値になる**条件、あるいは
**2 つの指標が必ず一致してしまう**条件がないかを確かめる。

- 正規化の基準を入力自身から作ると、比は定数になる。
  例: 頭部基準が無いとき「対象全体の bbox」で正規化 → `幅/基準幅` は
  形状によらず必ず 1.0、上端は必ず +1、下端は必ず −1。3 つの別形状で実測して確認できた。
- 派生量が「A と B の差」なら、A と B が同じ源から来ていないかを見る。
  例: `custom_vs_geo` は常に 0.0° だった。両方とも同じカスタム法線を読んでいたため。

見つけたら **値を埋めずに欠測として出す**。定数は「測れた」ように見えるぶん、
欠測より有害で、そのまま記録に転記される。

## 原則5: 警報系は「鳴らない方向」も試す

★・警告・アラート・「問題なし」を出す道具は、**鳴る側だけ**テストされがち。
本当に危ないのは、問題があるのに鳴らない側。

- 同一入力を 2 つのバージョンで比べたら偽の警報が並ぶ → 誤検知
- 比較対象が丸ごと欠損しているのに警報 0 件 → **最大の欠落が最も静かに通る**

どちらも実際に起きた。**「異常なし」が本当に「調べた上で異常なし」なのか、
「調べられなかった」なのかを、出力上で区別できるようにする。**
未測定と正常を同じ見た目にしない。

## 原則6: テストが構造的に届かない経路を、別ルートで通す

外部ランタイム（ゲームエンジン、DCC ツール、GPU、OS API、SaaS）に依存する部分は、
単体テストが原理的に届かない。そこに手を付けないまま「テストは全部通った」と
言うと、通っていない範囲がそのまま残る。

- まず **どの関数が一度も実行されていないか**を名指しする
- 次に、その環境を手に入れる道を探す。**手に入らないと決めつけない。**
  ホストアプリの Python モジュールが単体で配布されていることは珍しくない
  （実例: `pip install bpy` で Blender 4.5 の API がそのまま動き、
  合成シーンを組んで初回実行できた）
- 通した結果、**その場で 2 件の実バグが出た**。どちらも合成データの自己テスト
  98 項目では原理的に出ない種類のもの

環境を用意できないときは、**依存部分を純関数に切り出してテスト可能にする**。
例: 「ボーン階層の要約」を「名前→親名の辞書を受け取る純関数」に分ければ、
エンジン無しで回帰テストできる。

## 原則7: 記録した数値の出所を取り違えない

指標が正しくても、記録が間違えば同じ害になる。特に多いのが 2 つ:

- **集計値を個体値として引用する。** 「この板のプロファイルは [...]」と書いた値が、
  実は複数個体の中央値だった、という取り違えが実際に起きた。
  転記するときは、その値が **1 個体のものか、集団の要約か**を必ず区別する。
- **文書とコードのバージョンがずれる。** 文書だけ版を上げて実装の版を上げ忘れると、
  出力の表示と記録が食い違い、後から「どちらが正しいか」を判定できなくなる。

再現手順を書けない数値は、記録しても次に使えない。
**「どの入力で、どの設定で出したか」まで書いて初めて実測値になる。**

## 手順: 定着させる前の自己監査

指標を実装したら、コミットや公開の前にこれを通す。

1. **問いを書く**（原則1）。指標ごとに一文。
2. **交絡を列挙する**（原則2）。1 つも思いつかないときは、
   まだ指標を疑えていない可能性が高い。名前ではなく式から考え直す。
3. **弁別ケースを作って順序を見る**（原則3）。分離不能なら式を作り直す。
4. **定数化・恒等崩壊を探す**（原則4）。正規化の基準と派生量を重点的に。
5. **警報の鳴らない側を試す**（原則5）。
6. **未実行の経路を名指しし、通す道を探す**（原則6）。
7. 見つけた誤りは、**その入力をそのまま回帰テストにする**。
   「本物より偽陽性の方が高スコアだった」ケースは特に価値が高い。
   後から式を触ったときに、同じ穴に落ちたことが即座に分かる。

### 独立した目を入れる場合

規模が大きいときは、観点を分けて並列にレビューさせ、
出た指摘を **反証する側**に回して検証すると精度が上がる。

- レビューは観点ごとに分ける（正しさ / 統合 / 文書との整合 / 未実行経路 / 性能）
- 各指摘は「再現できるか」「既に手当て済みでないか」「実際に影響するか」の
  独立した観点で潰しにかかる。**既定を『棄却』にする**と、
  もっともらしいだけの指摘が残らない
- 生き残った指摘だけを直す

実例では 34 件の候補のうち、この検証を通ったものだけが実際の欠陥だった。

## 適用範囲

「自分で決めた式やルールで、何かを判定・採点する」もの全般。

健全性スコア / KPI / SLO の指標 / lint・静的解析のルール /
異常検知のしきい値 / eval や採点の基準 / A-B テストの評価指標 /
レコメンドのスコア / 品質ゲート / 分類ラベルの定義 /
計測スクリプトが出す派生量。

既にある標準的な指標を計算するだけなら不要。
**自分で定義した瞬間**にこの skill の出番になる。

実例の詳細（数値付き）は `references/case-studies.md` を参照。
どれも「テストは全部通っていた」状態で見つかったもの。
