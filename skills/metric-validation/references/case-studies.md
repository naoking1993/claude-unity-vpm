# 実例集: テストを全部通っていたのに間違っていた指標

すべて 1 つのプロジェクト（Blender の髪メッシュを解析するスクリプト）で
実際に起きたもの。当時 55 項目の自己テストが全部通っていた状態で見つかった。
数値はすべて実測値。

---

## 1. 中膨れ率 — 判別式そのものが間違っていた（最重要）

**問い**: この板は中央が両端より太いか。

**実装**: `bulge = w50 / ((w0 + w100) / 2)`（中央幅 ÷ 両端の**平均**）

**何を測っていたか**: 幅プロファイル曲線の**凸性**。中央が太いかどうかではなく、
細り方が線形からどれだけ外れているか。

**弁別ケースと実測値**

| 幅プロファイル | 実態 | bulge | v1 の判定 |
|---|---|---|---|
| 1.00 → 0.55 → 0.10 | 線形テーパ | 1.000 | taper_linear ✓ |
| 1.00 → 0.30 → 0.10 | **単調に細るだけ** | 0.545 | **waisted（中細り）✗** |
| 1.00 → 0.90 → 0.10 | **単調に細るだけ** | 1.636 | **mid_bulge（中膨れ）✗** |
| 1.0 → 1.0 → 1.0 → 0.64 → 0.28 | 幅を保って急に細る | 1.562 | **mid_bulge ✗** |
| 1.0 → 1.147 → **1.198** → 1.115 → 1.008 | **本物の中膨れ** | **1.193** | mid_bulge ✓ |

**決定的だった点**: 本物の中膨れ **1.193** より、偽陽性 **1.453〜1.636** の方が
スコアが高い。**どんな閾値を選んでも分離できない**ので、
閾値の校正では直らないことがこの 2 行で確定した。

**修正**: 「両端の平均」ではなく「両端の**どちらか**」と比べる。

```
bulge = w50 / max(w0, w100)   # >1.1 で中膨れ（中央が両端のどちらより太い）
waist = w50 / min(w0, w100)   # <0.9 で中細り（中央が両端のどちらより細い）
```

凸性は捨てずに `width_curvature_ratio` として別名で出す（情報としては有用）。
上の 5 ケースすべてが正しく分類されるようになった。

## 2. レイヤー判定 — 交絡因子が支配していた

**問い**: この房は頭からどれだけ外側の層にあるか。

**実装**: 頭部中心からの 3D 距離 `sqrt(x² + y² + z²)`（正規化済み）

**何を測っていたか**: 「外側にあるか」と「下に長く垂れているか」の**合成**。
z 成分が入るため、長い房ほど自動的に「外側」になる。

**弁別ケースと実測値**（頭部 half=(0.1, 0.1, 0.12)）

| 房 | 中点座標 | 3D 半径 | 水平半径 |
|---|---|---|---|
| 頭皮に密着した短い房 | (0.100, 0, 0.000) | 1.000 | 1.000 |
| **頭皮に密着した長い房** | (0.090, 0, −0.180) | **1.749** | 0.900 |
| **外側に膨らんだ短い房** | (0.140, 0, 0.000) | **1.400** | 1.400 |

密着した房（1.749）が、実際に膨らんだ房（1.400）より外側と判定される。
**順序が反転している。**

**修正**: 層は**水平半径** `sqrt(x² + y²)` で測る。
さらに、頭部より下（z_norm < −1.0）まで垂れた房には層が定義できないので
`below_head` として層の判定から外す。埋めるより外す方が正しい。

## 3. 「幾何法線」— API が別のものを返していた

**問い**: カスタム法線は、幾何法線からどれだけずらされているか（球体転写の検出）。

**実装**: `vertices[].normal`（幾何法線のつもり）と `corner_normals`（カスタム法線）の角度差。

**何が起きたか**: Blender 4.x では、カスタム分割法線が存在すると
`vertices[].normal` と `vertex_normals` は**カスタム法線そのものを返す**。
汚染されないのは `polygons[].normal` だけ。

**弁別テスト**: カスタム法線**だけ**を +Z に差し替えて、幾何法線の値が動くか見た。

| 読み出し先 | カスタム法線=放射 | カスタム法線=+Z |
|---|---|---|
| `vertices[0].normal` | (−0.294, −0.713, 0.637) | **(0, 0, 1) ← 追従した** |
| `corner_normals[0]` | (−0.294, −0.713, 0.637) | (0, 0, 1) |
| `polygons[0].normal` | (0, 0.998, −0.062) | **(0, 0.998, −0.062) 不変** |

集計値も `geo 4.0° / custom 4.0° / 差 0.0°` → `geo 85.4° / custom 85.4° / 差 0.0°` と
**両方が一緒に動き、差は常に 0.0°**。この指標は最初から何も判定できていなかった。

**修正**: 面法線を面積で重み付けして頂点に積み、幾何法線を自前で作る。
修正後は geo が 90.9° で固定され、custom だけが 4.0° / 85.4° と動く。

**教訓**: 名前が `normal` でも、その処理系のその条件下で期待どおりとは限らない。
**入力の片方だけを動かして出力が動くか**を見れば一発で分かる。

## 4. チェーン根の親 — 「集合の定義」が答えを決めていた

**問い**: 髪のボーンチェーンは何にぶら下がっているか。

**実装**: 頂点グループ名と一致するボーンを集めてチェーンとみなし、
親を辿って親がチェーン内に無いものを「チェーン根」、その親を答えとする。

**何が起きたか**: 髪の根元は Head ボーンにウェイトされるのが標準構成なので、
`Head` も「一致するボーン」に入る。すると **Head 自身がチェーン根**になり、
答えは「Head の親」（= None や Neck）になった。
`max_chain_depth` も Head を数えて 4（正しくは 3）。

つまり **VRChat 向けの髪の標準構成でちょうど無意味になる**指標だった。

**修正**: Head 系ボーンをチェーンから除いてから解析する。
修正後 `chain_root_parent_mode = "Head"` / `max_chain_depth = 3`。

**教訓**: 集合に対する集計は、**何をその集合に入れたか**で答えが変わる。
「一致するもの全部」は定義として弱い。

## 5. 比較ツールの ★ — 両方向とも壊れていた

★ は「元と再生成で差が大きい項目」＝直すべき欠落を指すマーク。

**誤検知側**: 片方の JSON にキーが無いだけで「0 件 vs N 件」として ★ を付けていた。
**同一メッシュ**を旧バージョンと新バージョンで解析して比べるだけで偽の欠落が並ぶ（★2）。

**見逃し側**: 逆に、比較対象の集計ブロックが**丸ごと空**でも ★ は 3 件しか出なかった。
欠測は ★ を増やさない実装だったため、**最大の欠落が最も静かに通る**。

**修正**: 「片方に項目が無い」を欠測として別枠で数え、件数と
バージョン不一致をフッタに明示する。
同一メッシュの旧新比較は ★0 ／ 未測定 50、空ブロックは 未測定 52 と表示されるようになった。

**教訓**: 警報系は鳴る側だけ試しがち。
**「異常なし」が「調べた上で異常なし」なのか「調べられなかった」なのか**を
出力で区別できないと、後者が前者に化ける。

## 6. エンベロープ指標 — 基準を入力自身から作ると定数になる

頭部基準が見つからないとき、対象全体の bbox を代用していた。
すると髪は自分の bbox をちょうど埋めるので:

| 形状 | bbox_norm.x | top_z_norm | bottom_z_norm | widest_band |
|---|---|---|---|---|
| 縦長 | **1.0** | **1.0** | **−1.0** | crown |
| 横長 | **1.0** | **1.0** | **−1.0** | crown |
| 立方 | **1.0** | **1.0** | **−1.0** | crown |

3 つの別形状で**全部同じ値**。形状の情報がゼロなのに、数値としては出てしまう。
当時の警告は「同一設定同士の比較のみ有効」だったが、
これらは同一設定同士でも比較できない。

**修正**: 該当項目を欠測（None）にし、`degenerate_under_fallback` フラグと
比較可能な縦横比だけを残す。

**教訓**: 正規化の基準を入力自身から作ると、比が定数化する。
**「この値が入力によらず一定になる条件はあるか」**を必ず一度考える。

## 7. 集計値を個体値として引用した

記録に「先細り板のプロファイルは `[1.0, 0.827, 0.685, 0.473, 0.37]`」と書いたが、
これは **カード＋筒の 2 個体の中央値**で、板単体の値は
`[1.0, 0.809, 0.682, 0.491, 0.363]` だった。

数値としては近いので、見ただけでは気づけない。
出所（どの JSON キーか）まで書く習慣が無いと防げない。

**教訓**: 転記する値が **1 個体のものか集団の要約か**を、書く時点で区別する。

## 8. 一度も実行されていなかった経路

外部ランタイム（Blender の `bpy`）に依存する関数群
（`run_blender` / `bl_mesh_data` / `bl_find_head` / `bl_bone_summary`）は、
合成データの自己テストが原理的に届かない。
「テスト 55 項目が全部通った」は、この範囲について何も言っていなかった。

**通した方法**: ホストアプリの Python モジュールが単体配布されていた
（`pip install bpy==4.5.13`、Python 3.11 用の wheel）。
合成シーン（カード 6 枚・頭・ボーン・カスタム法線・Mirror）を組んで初回実行。

**結果**: その場でケース 3 とケース 4 が出た。どちらも合成データのテストでは
原理的に出ない種類のもの。

**あわせて分かった実測事実**（想定と違っていた）:
FBX 書き出しは既定設定（`use_mesh_modifiers=True`）でモディファイアを形状に焼き込み、
**シェイプキーを落とす**（頂点 288 → 576、シェイプキー消失）。
`False` なら逆。つまり「モディファイアが無い FBX ＝片側だけ」とも
「シェイプキーが無い＝作者が作らなかった」とも読めない。

**教訓**: 環境が手に入らないと決めつける前に探す。
手に入らないときは、依存部分を純関数に切り出してテスト可能にする
（ケース 4 の修正では「名前→親名の辞書を受け取る純関数」に分離し、
Blender 無しで 7 件の回帰テストを書けるようにした）。
